# v3 vs v2

How HomotopyContinuationNext.jl (v3) differs from HomotopyContinuation.jl (v2), and why.

**Reproduce:**
- `make compare` — v3/v2 eval/jac/build ratios + v2 interpreted-vs-compiled comparison
- `julia --project=benchmark benchmark/compare/ttfx.jl` — TTFX (must be a fresh Julia session)
- `make benchmark` — steady-state timings
- `make test` runs the full test suite (`test/instruction_count_test.jl` covers instruction-count regressions)

## The Core Design Problem in v2

In v2, every polynomial system gets a **unique type**. `CompiledSystem{ID}` stores a hash of the
expression tree as a type parameter:

```julia
# v2: src/model_kit/compiled_system_homotopy.jl
struct CompiledSystem{HI} <: AbstractSystem   # HI = (hash::UInt, collision_idx::Int)
    nexpressions::Int
    nvariables::Int
    nparameters::Int
    system::System
end
```

The hash is computed from the symbolic expressions and used to key `@generated` function
specializations. When Julia sees `evaluate!(u, ::CompiledSystem{(0xabc, 1)}, x)`, it generates
and compiles evaluation code specific to that system.

The problem is that this type parameter **propagates through the entire stack**:

```
CompiledSystem{(0xabc, 1)}
  → MixedSystem{(0xabc, 1)}                               # wraps compiled + interpreted
    → StraightLineHomotopy{MixedSystem{(0xabc, 1)}}       # homotopy parameterized by system
      → Tracker{StraightLineHomotopy{MixedSystem{(0xabc, 1)}}, Matrix{ComplexF64}}
        → EndgameTracker{StraightLineHomotopy{...}, Matrix{ComplexF64}}
          → Solver{EndgameTracker{...}}
```

Every new polynomial system = new hash = **every struct in the chain becomes a new type**.
Julia must recompile the tracker, Newton corrector, predictor, endgame, and solver from scratch.
That's the **28 second first-solve wall**.

v2 actually has `InterpretedSystem` (`:none` mode) which has no type parameter and achieves 1.1s
TTFX. But `:mixed` (which inherits the type parameter) is the default because it was believed
to be faster. Benchmarking shows the speed difference is only a few percent
(reproduce: `benchmark/compare/v2_modes.jl`).

## How v3 Fixes This

v3 inserts a **type firewall** via `FunctionWrapper`:

```julia
# v3: src/core/system_evaluator.jl
struct SystemEvaluator                          # NO type parameters
    _evaluate!::SysEvalFW                       # FunctionWrapper{Nothing, Tuple{FSVec, FSVec, FSVec}}
    _df64::Base.RefValue{SysEvalDF64Pair}       # extended precision, installed on first use
    _install_df64!::SysDF64InstallFW
    _evaluate_and_jacobian!::SysEvalJacFW
    _taylor_1!::SysTaylor1FW
    _taylor_2!::SysTaylor2FW
    _taylor_3!::SysTaylor3FW
    _size::Tuple{Int,Int}
    _nparameters::Int
end
```

The compiled evaluation code lives **inside** the `FunctionWrapper` closures — it captures the
`Interpreter` by reference. The struct type is always the same regardless of what system it wraps.

The type chain becomes:

```
SystemEvaluator                          # always the same concrete type
  → HomotopyEvaluator                   # always the same concrete type
    → Tracker                            # always the same concrete type — compiled ONCE
```

`FunctionWrapper` calls are statically dispatched through a function pointer — no dynamic dispatch,
no boxing. The tracker never knows or cares what polynomial system it's tracking.

## Where v3 Wins: Architecture, Performance, and Predictability

v3 wins on multiple fronts: predictable compilation, pure Julia internals, and faster
end-to-end solving than v2 (total-degree solving is 1.8x to 3.6x faster; polyhedral matches v2
within noise). v3 has reached full v2 parity on the core solve pipeline plus the endgame,
threading, overdetermined systems, parameter homotopies, monodromy (with group actions and the
trace test), and certification.

### 1. Predictable compilation (no TTFX pathology)

Reproduce: `julia --project=benchmark benchmark/compare/ttfx.jl` (fresh session required).

| Metric | Time |
|--------|------|
| v3 package load | 0.77s |
| v3 construction + init + first solve | ~9.8s |
| **v3 total (cold)** | **~10.6s** |
| v2 package load | 1.30s |
| v2 first solve `[:mixed]` (total) | 45.1s |
| v2 first solve `[:none]` | 10.8s |
| v2 second system `[:mixed]` | 5.7s (still recompiling) |

v3 is over 4x faster than v2's default `:mixed` mode, whose `CompiledSystem{ID}` triggers full
pipeline recompilation per system. v2's `:none` mode (no type parameter) is comparable to v3's
cold total. The win is against v2's per-system recompilation pathology, not against all v2 usage.
The 0.77s core load holds because certification (the sole Arblib consumer) is a separate `lib/`
subpackage; see `02_status.md` for the full TTFX breakdown.

### 2. Pure-Julia symbolic pipeline

v2 uses SymEngine (C FFI) for symbolic manipulation and CSE. This causes precompilation issues,
reinitialization bugs (#643), and makes debugging difficult — stack traces cross the Julia/C boundary.

v3 uses DynamicPolynomials for user input and `MP.differentiate` for symbolic Jacobians. The CSE
algorithm is a pure-Julia port of SymEngine's `cse.cpp` (same two-phase algorithm: `opt_cse` for
common argument factoring, `tree_cse` for repeated subexpression elimination). Fully precompilable,
fully debuggable.

### 3. Single evaluation code path

v2 has three evaluation modes with separate system types:

| Mode | Type | Eval | Taylor | Type param? |
|------|------|------|--------|-------------|
| `:all` | `CompiledSystem{ID}` | `@generated` native code | `@generated` native code | Yes |
| `:mixed` (default) | `MixedSystem{ID}` | `@generated` via `CompiledSystem` | Interpreter | Yes |
| `:none` | `InterpretedSystem` | Interpreter | Interpreter | No |

v3 has one: interpreter. The same `InstructionSequence` drives all evaluation modes (F64, DF64,
Taylor orders 1-3) through generic dispatch on the tape element type. No mode selection, no
dual-track complexity.

v3 now has an opt-in `CompileMode.COMPILED` mode that uses RuntimeGeneratedFunctions to
compile eval and Jacobian to native code (3–6x kernel speedup). Taylor and DF64 stay
interpreted. The FunctionWrapper firewall means the tracker is identical regardless of mode.

```julia
System(F; compile = CompileMode.COMPILED)   # RGF-compiled eval+jac
System(F; compile = CompileMode.INTERPRETED) # tape interpreter (default)
```

Default is `INTERPRETED` to preserve TTFX behavior. `COMPILED` adds ~1s to first solve
and ~1.3x to build time (`make benchmark` → compile_modes group).

### 4. Pure-Julia system construction

v2 builds via SymEngine FFI → `InterpretedSystem`. v3 does everything in pure Julia:
`poly_to_sexpr` → CSE → `TapeCompiler` → `InstructionSequence`. Build times are comparable
(v3 ~1.3x faster median, see `benchmark/compare/interpreter.jl`).

### 5. Concrete array types without size in type parameter

v2 uses `Matrix{ComplexF64}` as a type parameter in `Tracker{H, M}` and uses `StaticArrays`
in some places (size baked into type → specialization explosion for different dimensions).

v3 uses `FSVec{T}` / `FSMat{T}` from FixedSizeArrays.jl — non-resizable arrays where size is
a runtime value in a field, not a type parameter. `FSMat{ComplexF64}` is the same concrete type
whether it's 4x4 or 100x100. The tracker has zero type parameters.

### 6. Fewer dependencies, less invalidation

v2 dependencies removed in v3: SymEngine, Symbolics, LoopVectorization (~5500 invalidations per
see `benchmark/compare/ttfx.jl`), StructArrays, Parameters, Reexport, SimpleGraphs, LRUCache.

v3 new deps: Moshi (tagged unions for SExpr/ExecInstruction ADTs), EnumX (scoped enums).
Both are lightweight with minimal invalidation.

The one heavy dependency certification needs, Arblib (a C binary that adds roughly 0.8s of load
time and thousands of invalidation descendants), is kept out of core entirely by putting
certification in the `HomotopyContinuationNextCertification` subpackage. Users who never certify
never pay for Arblib.

### 7. Immutable result types

v2: `PathResult` is mutable — internal code mutates fields after construction.

v3: `PathResult` is immutable with `EnumX` scoped return codes (`PathResultCode.PATH_SUCCESS`
instead of `:success`). Type-safe, faster comparison, cannot be accidentally mutated.

## Steady-State Performance

### v3 interpreter vs v2 interpreter

From `benchmark/compare/interpreter.jl` — v3 interpreter vs v2 `InterpretedSystem`
(both tape-based, same polynomial systems). Ratio > 1.0 = v3 faster.

| Metric | Min | Median | Max |
|--------|----:|-------:|----:|
| Eval | 0.70x | 1.25x | 1.55x |
| Jac | 1.21x | 1.39x | 1.82x |
| Build | 1.18x | 1.31x | 2.17x |

Systems tested: cyclic-5/6/7, chain-5/6/7, random sparse 6x6 (8 systems total).
v3 is ~25% faster on eval (median) and ~39% faster on Jacobian. Build time is comparable.

### v2 interpreted vs v2 compiled

From `benchmark/compare/v2_modes.jl` — v2's own `InterpretedSystem` vs `CompiledSystem`.
Ratio = interpreted/compiled (1.0 = same speed, higher = interpreted slower).

| Metric | Min | Median | Max |
|--------|----:|-------:|----:|
| Eval | 3.54x | 4.43x | 7.83x |
| Jac | 6.85x | 9.63x | 12.74x |

v2's compiled mode is significantly faster than interpreted for raw eval/jac.

### End-to-end solve (the bottom line)

v3 is now **2-3x faster** than v2 on katsura systems with endgame enabled.

From `benchmark/compare/tracking.jl` (`CompileMode.COMPILED`, fixed seed `0x4567`):

| System | v3/v2 wall time | v3 total steps/path | v2 total steps/path |
|--------|----------------:|--------------------:|--------------------:|
| katsura-3 | **2.99x** | 36.5 (292 acc, 0 rej) | 87.0 (696 acc, 0 rej) |
| katsura-4 | **2.01x** | 48.6 (777 acc, 0 rej) | 78.8 (1260 acc, 0 rej) |
| katsura-5 | **1.96x** | 56.7 (1814 acc, 0 rej) | 98.5 (3137 acc, 15 rej) |

v3 takes fewer steps per path than v2 (better Padé predictor after the `taylor_op_sqr` fix),
and each step is cheaper (compiled evaluation, monomorphic tracker). Both factors combine for
the wall-time advantage.

## Where v3 Still Lags

Most gaps listed in earlier drafts are now closed. Now at full v2 parity:
**threading** (`Threaded()` executor, the default), **overdetermined systems**
(`RandomizedSystem` square-up + excess-solution filtering), **monodromy**
(`monodromy_solve` with parameter loops, trace test, `UniquePoints` dedup, group actions),
**certification** (the `HomotopyContinuationNextCertification` subpackage), **progress bars**
(`ProgressMeter` integration), and the **endgame** (`EndgameTracker`).

The remaining true gaps versus v2:

### 1. Witness sets and numerical irreducible decomposition (NID)

**Affine case done; projective/parametric remain.** v3 now computes witness sets and the numerical
irreducible decomposition for affine systems (`witness_set`, `trace_test`, `membership`,
`regeneration`, `decompose`, `nid`), validated at v2 parity (two circles give 2 components of
degree (2,2); the multi-dimensional example gives 11 components matching v2's degree table). The
redesign stays in ambient coordinates and appends the linear equations `A x − b` (v2's
`SlicedSystem`), so witness init reuses the total-degree `solve`, moves reuse
`ExtrinsicSubspaceHomotopy`, the u-homotopy reuses `StraightLineHomotopy`, and fill-up/decompose
reuse `MonodromySolver`. Remaining: projective/homogeneous witness sets and `trace_test`
(chart-consistent moves), witness sets of a `fix_parameters` system, and threaded
intersection/membership. See `02_status.md`.

### 2. MPI path tracking

**Impact: LOW.** v3 goes beyond v2 here: v2 has no multi-process path tracking at all, while v3
adds `DistributedExecutor` (Distributed.jl, in a package extension) alongside `Threaded()`. What
is missing is an MPI backend for clusters whose scheduler will not launch Distributed workers.
The transport calls are isolated behind a handful of internal functions so a second backend is
one added file, but MPI is SPMD and needs its own entry point rather than a driver calling
`solve`. Monodromy is covered too, by handing out only its loop tracking.

### 3. Non-polynomial (rational and analytic) expression input

**Impact: MEDIUM.** v2's ModelKit builds straight-line programs, so systems with rational
subexpressions (`u₁/x² + u₂`, `y[1:2] ./ y[3]`) work directly. The intended v3 frontend also
includes parameter-dependent unary expressions such as `sqrt(γ) * x₁ + x₂^2`, `sin(γ) * x₁`,
and `cos(x₁) - x₂`. v3's DynamicPolynomials input layer is polynomial-only, but the interpreter
retains `OP_SQRT`, `OP_SIN`, and `OP_COS` in preparation for that frontend. This blocks two v2
monodromy testsets and one v2 certification testset. The implementation and validation checklist
is maintained in `02_status.md`.

### 4. System composition

**Impact: LOW/MEDIUM.** v2's `CompositionSystem` (`L₂ ∘ f ∘ L₁`) has no v3 equivalent (blocks the
v2 symmetroids monodromy test; the custom-`distance` kwarg it also used is already supported).

### 5. Group-action symmetry in `Result` clustering

**Resolved, and ahead of v2.** `recluster(::Result; group_action, group_actions, atol, rtol)`
merges proximity clusters that share an orbit, so `nsolutions`/`results`/`solutions` count orbits
while `multiplicity` keeps reporting the multiplicity of the root; `clusters` / `cluster_of` read
the partition back out. v2 has no equivalent: its `compute_multiplicities` takes `kwargs...` and
discards them, so v2's `Result` dedup is never symmetry-aware, and it exposes duplicates only as
a `multiple_indicator::Set{Int}` of path numbers rather than as groups.

### 6. Multi-homogeneous variable groups

**Impact: LOW.** No `variable_groups` / `MultiBezoutIterator`. Polyhedral homotopy already gives
BKK-optimal path counts for most cases where multi-homogeneous tracking would help.

## API Differences

| Operation | v2 | v3 |
|-----------|----|----|
| Basic solve | `solve(F)` | `solve(F)` (same) |
| System construction | Implicit in `solve()` | Explicit `System(polys)`, reusable |
| Start system | `:polyhedral` (default) | `Polyhedral()` / `TotalDegree()` types |
| Parameter homotopy | `solve(F, starts; p₁, p₀)` | `solve(F, starts, p₁, p₀)` (positional ends) |
| Many targets | `solve(F, starts; target_parameters = [q₁, …])` | `solve_targets(F, starts, p₁, targets)` (own verb, returns a `Vector`) |
| Fix parameters | `solve(F; target_parameters = p)` | `solve(fix_parameters(F, p))` |
| Result access | `solutions(r)`, `nreal(r)` | Same API + `nresults`, `multiplicity`, `results` |
| Solution dedup | `nresults` via VoronoiTree | `nresults` via O(k²) proximity clustering |
| Custom system | Subtype `AbstractSystem` | Same interface, but `FSVec`/`FSMat` passed instead of `Vector`/`Matrix` (transparent via `AbstractVector`) |
| Return codes | Symbols (`:success`) | Scoped enums (`PathResultCode.PATH_SUCCESS`) |
| Compiled mode | `compile=:all` | `compile=CompileMode.COMPILED` (opt-in, RGF-based) |
| Singular detection | `is_singular`, `nsingular` | Same API (v2 result parity) |
| At-infinity | `is_at_infinity`, `nat_infinity` | Same API |
| Endgame | Automatic | Automatic (EndgameTracker wraps Tracker) |
| Threading | Automatic | `Threaded()` executor (default) |
| Certification | `certify(F, result)` | `certify` in the `HomotopyContinuationNextCertification` subpackage |
| Monodromy | `monodromy_solve(F, sols, p)` | Same API (full v2 parity) |

## Remaining Work (priority)

Threading, overdetermined systems, monodromy, certification, progress bars, and the endgame are
done. What is left, roughly in priority order:

1. **Witness sets / NID**: affine core and `intersect` done; projective, parametric, and threaded
   intersection/membership remain
2. **Rational / analytic non-polynomial input**: unblocks several v2 tests and use cases
3. **MPI executor**: `DistributedExecutor` already scales every route past one process,
   so this is only for clusters that will not launch Distributed workers
4. **System composition**, **group-action `Result` clustering**, **multi-homogeneous groups**: smaller, lower priority
5. **Benchmark CI** and the **direct polynomial compiler**: infrastructure / experimental

See `02_status.md` for the full checklist.
