# v3 vs v2

How HomotopyContinuation.jl v3 differs from HomotopyContinuation.jl v2, and why.

Last updated: 2026-09-14, against upstream v2.22.4.

During the rewrite, v3 used the temporary package name `HomotopyContinuationNext` so v2 and v3
could coexist in one Julia environment. PR #12 restores the registered `HomotopyContinuation`
name and UUID for the v3 release line.

## Reproduce

- `make benchmark` — steady-state v3 timings
- `make ttfx` — fresh-session v3 TTFX inventory
- `make test` — core plus certification suite

The old same-process `make compare` harness is intentionally disabled after restoring the package
identity. v2 and v3 now correctly share one package name and UUID, so live v2/v3 comparison must
use isolated Julia environments/processes. Historical comparison measurements below remain useful;
the fixed v2 parity regressions remain active in the ordinary suite.

## Bottom line

v3 is **feature/capability complete relative to v2.22.4**. The remaining work is API freeze,
release documentation, v3-specific cleanup and performance characterization, not missing v2
functionality.

The parity claim is based on:

1. the July/August testset-by-testset comparison against the v2 suite;
2. the August re-audit against v2.22.1;
3. the September catch-up for the final v2.22.x changes;
4. validation of the integrated merged v3 tree through the permanent CI matrix.

See `09_v2_parity_freeze.md` for the final catch-up record.

## Package identity

v3 is a new major version of HomotopyContinuation.jl, not a separate registered package. Its
release-facing identity is therefore:

```text
name = HomotopyContinuation
uuid = f213a82b-91d6-5c5d-acf7-10f1c761b327
version = 3.0.0-DEV
```

The temporary `HomotopyContinuationNext` identity was development scaffolding. It must not become
part of the public v3 API. The certification split remains a separate package, now named
`HomotopyContinuationCertification`.

This identity restoration has one intentional tooling consequence: a single Julia environment can
no longer resolve both v2 and v3 as distinct package dependencies. Optional live comparisons must
spawn isolated environments. Tests under `test/compat/` are temporary forwarding infrastructure
for migrating the large behavioral test corpus; JET/Aqua/import/concrete-struct/TTFX gates target
the real `HomotopyContinuation` module directly.

## The core design problem in v2

In v2, compiled polynomial systems carry a system-specific identity in their type. That identity
propagates through the homotopy, tracker, endgame and solver stack, so a new polynomial system can
force Julia to specialize and compile a large fraction of the numerical pipeline again.

Conceptually:

```text
CompiledSystem{system_id}
  -> homotopy{CompiledSystem{system_id}}
    -> tracker{homotopy{...}}
      -> endgame{...}
        -> solver{...}
```

## The v3 type firewall

v3 separates system-specific evaluation code from the solver type domain. `SystemEvaluator` and
`HomotopyEvaluator` are concrete monomorphic firewalls whose callable kernels live behind
`FunctionWrapper`s. A tracker sees the same concrete evaluator type regardless of the polynomial
system.

```text
SystemEvaluator
  -> HomotopyEvaluator
    -> Tracker
      -> EndgameTracker
```

The central invariant is therefore:

```text
system-specific compiled code != system-specific solver type
```

## Important API differences

v3 deliberately does not reproduce every v2 spelling or architecture.

| Operation | v2 | v3 |
|---|---|---|
| Basic solve | `solve(F)` | `solve(F)` |
| System construction | often implicit | explicit reusable `System(...)` |
| Start-system choice | keywords/symbols | typed algorithms (`TotalDegree()`, `Polyhedral()`) |
| Compile mode | `compile=:none/:mixed/:all` | `CompileMode.INTERPRETED/COMPILED/COMPILED_ALL` |
| Many targets | keyword-driven | explicit `Sweep()` route |
| Fix parameters | target-parameter kwargs | `fix_parameters(F, p)` |
| Parallelism | `threading::Bool` style | positional executor (`Serial`, `Threaded`, `DistributedExecutor`) |
| Monodromy | `monodromy_solve(...)` | `solve(..., Monodromy())` |
| Certification | core package | `HomotopyContinuationCertification` package |
| Return codes | symbols | scoped enums |
| Options | keyword bags on verbs | typed algorithm/options structs |

Exact name-level API identity is not the parity criterion. Capability and numerical behavior are;
the final supported public v3 surface still needs an explicit release freeze.

## Where v3 goes beyond v2

1. **Compilation predictability.** The monomorphic evaluator firewall prevents a new input system
   from creating a new tracker/endgame type chain.
2. **Pure-Julia symbolic/evaluation pipeline.** Polynomial and expression front ends lower into a
   shared instruction representation, with pure-Julia CSE and optional RGF code generation.
3. **Lightweight core / certification split.** Arblib is isolated in
   `HomotopyContinuationCertification`.
4. **Distributed execution.** `DistributedExecutor` provides multi-process tracking and
   monodromy.
5. **Lossless NID incompleteness.** Exhausting the decomposition budget retains unresolved witness
   orbits as `Irreducibility.UNKNOWN`.
6. **Stronger expression/certification stack.** Principal-branch behavior and branch-cut rejection
   are explicit across the shared operation vocabulary.

## September 2026 late-v2 catch-up

Relevant late-v2 changes represented in v3 include:

- non-finite predictor trust-region fallback;
- NID randomization and tolerance propagation;
- full/zero-dimensional `LinearSubspace` support;
- corrected witness/intersection coordinate contracts;
- Taylor positive-integer powers at zero constant term;
- principal-branch `log`;
- monodromy endpoint-admission hardening;
- fixed-parameter custom homotopies.

Two upstream changes are architecture-specific rather than missing capabilities: v2's global
compiled-cache locking has no analogue because v3 has no global per-system compile table, and v2's
polyhedral progress plumbing follows a MixedSubdivisions call path replaced by v3's canonical
mixed-cell construction.

## NID policy difference

v2 substantially increased its default decomposition iteration allowance. v3 currently keeps
`max_iters = 50`, but exhaustion is lossless: unresolved points remain as `UNKNOWN` witness sets
and are exposed through `unresolved_witness_sets` / `unresolved_degree`. Changing the default is a
performance/usability decision, not a parity fix.

## Performance snapshot

Historical development measurements showed total-degree solving about 1.8-3.6x faster than v2 on
the comparison set, polyhedral solving roughly at parity, and cold load + first solve around
10.6 s versus about 45 s for v2's default compiled route. These are development snapshots, not
release guarantees.

A final `COMPILED_ALL` versus v2 `:all` characterization remains useful, but the live harness must
now run v2 and v3 in isolated environments.

## What is intentionally not ported

The following are v2 implementation architecture rather than user capabilities:

- `CompiledSystem` / `InterpretedSystem` / `MixedSystem` as public architecture;
- global `set_default_compile` state and compiled-system caches;
- SymEngine-specific ModelKit internals;
- TreeViews/Juno display machinery;
- implementation-specific wrappers superseded by the v3 evaluator firewall.

## Remaining work

There are no known remaining v2 feature gaps. Before release:

1. certify the final package-identity-restoration PR as one integrated tree;
2. freeze the public API/extension surface;
3. finish release and migration documentation;
4. rebuild optional live v2/v3 comparisons around isolated environments;
5. characterize final benchmark/TTFX behavior;
6. address v3-specific cleanup without changing numerical semantics.
