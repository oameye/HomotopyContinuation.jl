# v3 vs v2

How HomotopyContinuationNext.jl (v3) differs from HomotopyContinuation.jl (v2), and why.

**Reproduce:**
- `make compare` — v3/v2 eval/jac/build ratios + v2 interpreted-vs-compiled comparison
- `julia --project=benchmark benchmark/compare/ttfx.jl` — TTFX (must be a fresh Julia session)
- `make benchmark` — steady-state timings
- `make test` — instruction counts

## The Core Design Problem in v2

In v2, every polynomial system gets a **unique type**. `CompiledSystem{ID}` stores a hash of the
expression tree as a type parameter:

```julia
# v2: src/model_kit/compiled_system_homotopy.jl
struct CompiledSystem{HI} <: AbstractSystem   # HI = (hash::UInt, collision_idx::Int)
    nexpressions::Int
    nvariables::Int
    nparameters::Int
    system::System
end
```

The hash is computed from the symbolic expressions and used to key `@generated` function
specializations. When Julia sees `evaluate!(u, ::CompiledSystem{(0xabc, 1)}, x)`, it generates
and compiles evaluation code specific to that system.

The problem is that this type parameter **propagates through the entire stack**:

```
CompiledSystem{(0xabc, 1)}
  → MixedSystem{(0xabc, 1)}                               # wraps compiled + interpreted
    → StraightLineHomotopy{MixedSystem{(0xabc, 1)}}       # homotopy parameterized by system
      → Tracker{StraightLineHomotopy{MixedSystem{(0xabc, 1)}}, Matrix{ComplexF64}}
        → EndgameTracker{StraightLineHomotopy{...}, Matrix{ComplexF64}}
          → Solver{EndgameTracker{...}}
```

Every new polynomial system = new hash = **every struct in the chain becomes a new type**.
Julia must recompile the tracker, Newton corrector, predictor, endgame, and solver from scratch.
That's the **28 second first-solve wall**.

v2 actually has `InterpretedSystem` (`:none` mode) which has no type parameter and achieves 1.1s
TTFX. But `:mixed` (which inherits the type parameter) is the default because it was believed
to be faster. Benchmarking shows the speed difference is only a few percent
(reproduce: `benchmark/compare/v2_modes.jl`).

## How v3 Fixes This

v3 inserts a **type firewall** via `FunctionWrapper`:

```julia
# v3: src/core/system_evaluator.jl
struct SystemEvaluator                          # NO type parameters
    _evaluate!::SysEvalFW                       # FunctionWrapper{Nothing, Tuple{FSVec, FSVec, FSVec}}
    _evaluate_df64!::SysEvalDF64FW
    _evaluate_and_jacobian!::SysEvalJacFW
    _taylor_1!::SysTaylor1FW
    _taylor_2!::SysTaylor2FW
    _taylor_3!::SysTaylor3FW
    _size::Tuple{Int,Int}
    _nparameters::Int
end
```

The compiled evaluation code lives **inside** the `FunctionWrapper` closures — it captures the
`Interpreter` by reference. The struct type is always the same regardless of what system it wraps.

The type chain becomes:

```
SystemEvaluator                          # always the same concrete type
  → HomotopyEvaluator                   # always the same concrete type
    → Tracker                            # always the same concrete type — compiled ONCE
```

`FunctionWrapper` calls are statically dispatched through a function pointer — no dynamic dispatch,
no boxing. The tracker never knows or cares what polynomial system it's tracking.

## Where v3 Wins: Architecture and Predictability

The main win is still architectural: predictable compilation behavior, pure Julia, and a
foundation that does not degrade as systems change. The regular-path tracker is also much closer
to v2 now than it was earlier in the rewrite, but the remaining late-path gap is still real
because endgame is missing.

### 1. Predictable compilation (no TTFX pathology)

Reproduce: `julia --project=benchmark benchmark/compare/ttfx.jl` (fresh session required).

| Metric | Time |
|--------|------|
| v3 first solve (total) | ~15s |
| v2 first solve `[:mixed]` (total) | ~47s |
| v2 solve-only `[:none]` | ~11s |
| v2 second system `[:mixed]` | ~6s (still recompiling) |

v3 wins against v2's default `:mixed` mode because `CompiledSystem{ID}` triggers full pipeline
recompilation per system. But v2's `:none` mode (no type parameter) is slightly faster than v3.
The win is against v2's per-system recompilation pathology, not against all v2 usage.

### 2. Pure-Julia symbolic pipeline

v2 uses SymEngine (C FFI) for symbolic manipulation and CSE. This causes precompilation issues,
reinitialization bugs (#643), and makes debugging difficult — stack traces cross the Julia/C boundary.

v3 uses DynamicPolynomials for user input and `MP.differentiate` for symbolic Jacobians. The CSE
algorithm is a pure-Julia port of SymEngine's `cse.cpp` (same two-phase algorithm: `opt_cse` for
common argument factoring, `tree_cse` for repeated subexpression elimination). Fully precompilable,
fully debuggable.

### 3. Single evaluation code path

v2 has three evaluation modes with separate system types:

| Mode | Type | Eval | Taylor | Type param? |
|------|------|------|--------|-------------|
| `:all` | `CompiledSystem{ID}` | `@generated` native code | `@generated` native code | Yes |
| `:mixed` (default) | `MixedSystem{ID}` | `@generated` via `CompiledSystem` | Interpreter | Yes |
| `:none` | `InterpretedSystem` | Interpreter | Interpreter | No |

v3 has one: interpreter. The same `InstructionSequence` drives all evaluation modes (F64, DF64,
Taylor orders 1-3) through generic dispatch on the tape element type. No mode selection, no
dual-track complexity.

v3 now has an opt-in `CompileMode.COMPILED` mode that uses RuntimeGeneratedFunctions to
compile eval and Jacobian to native code (3–6x kernel speedup). Taylor and DF64 stay
interpreted. The FunctionWrapper firewall means the tracker is identical regardless of mode.

```julia
System(F; compile = CompileMode.COMPILED)   # RGF-compiled eval+jac
System(F; compile = CompileMode.INTERPRETED) # tape interpreter (default)
```

Default is `INTERPRETED` to preserve TTFX behavior. `COMPILED` adds ~1s to first solve
and ~1.3x to build time (`make benchmark` → compile_modes group).

### 4. Pure-Julia system construction

v2 builds via SymEngine FFI → `InterpretedSystem`. v3 does everything in pure Julia:
`poly_to_sexpr` → CSE → `TapeCompiler` → `InstructionSequence`. Build times are comparable
(v3 ~1.3x faster median, see `benchmark/compare/interpreter.jl`).

### 5. Concrete array types without size in type parameter

v2 uses `Matrix{ComplexF64}` as a type parameter in `Tracker{H, M}` and uses `StaticArrays`
in some places (size baked into type → specialization explosion for different dimensions).

v3 uses `FSVec{T}` / `FSMat{T}` from FixedSizeArrays.jl — non-resizable arrays where size is
a runtime value in a field, not a type parameter. `FSMat{ComplexF64}` is the same concrete type
whether it's 4x4 or 100x100. The tracker has zero type parameters.

### 6. Fewer dependencies, less invalidation

v2 dependencies removed in v3: SymEngine, Symbolics, LoopVectorization (~5500 invalidations per
see `benchmark/compare/ttfx.jl`), StructArrays, Parameters, Reexport, SimpleGraphs, LRUCache.

v3 new deps: Moshi (tagged unions for SExpr/ExecInstruction ADTs), EnumX (scoped enums).
Both are lightweight with minimal invalidation.

### 7. Immutable result types

v2: `PathResult` is mutable — internal code mutates fields after construction.

v3: `PathResult` is immutable with `EnumX` scoped return codes (`PathResultCode.PATH_SUCCESS`
instead of `:success`). Type-safe, faster comparison, cannot be accidentally mutated.

## Steady-State Performance

### v3 interpreter vs v2 interpreter

From `benchmark/compare/interpreter.jl` — v3 interpreter vs v2 `InterpretedSystem`
(both tape-based, same polynomial systems). Ratio > 1.0 = v3 faster.

| Metric | Min | Median | Max |
|--------|----:|-------:|----:|
| Eval | 0.70x | 1.25x | 1.55x |
| Jac | 1.21x | 1.39x | 1.82x |
| Build | 1.18x | 1.31x | 2.17x |

Systems tested: cyclic-5/6/7, chain-5/6/7, random sparse 6x6 (8 systems total).
v3 is ~25% faster on eval (median) and ~39% faster on Jacobian. Build time is comparable.

### v2 interpreted vs v2 compiled

From `benchmark/compare/v2_modes.jl` — v2's own `InterpretedSystem` vs `CompiledSystem`.
Ratio = interpreted/compiled (1.0 = same speed, higher = interpreted slower).

| Metric | Min | Median | Max |
|--------|----:|-------:|----:|
| Eval | 3.54x | 4.43x | 7.83x |
| Jac | 6.85x | 9.63x | 12.74x |

v2's compiled mode is significantly faster than interpreted for raw eval/jac.

### End-to-end solve (the bottom line)

The old "v3 is clearly slower" summary is now stale. The latest katsura compare is around parity
or better in wall time, but the benchmark script still needs cleanup before those numbers should
be treated as hard claims.

From the current `benchmark/compare/tracking.jl` (`CompileMode.COMPILED`):

| System | v3/v2 time | v3 accepted steps/path | v2 accepted steps/path |
|--------|----------:|-----------------------:|-----------------------:|
| katsura-3 | ~1.86x | ~76.9 | ~62.9 |
| katsura-4 | ~1.33x | ~104.6 | ~75.6 |
| katsura-5 | ~1.01x | ~153.5 | ~89.8 |

Two important caveats:

- the current script is not using fixed seeds
- it reports accepted steps only, not total attempts

So the current result is best interpreted as: **the regular-path tracker improved a lot**, not
as: "v3 has definitively beaten v2 end-to-end".

## Where v3 Loses

### 1. Late-path tracker gap (raw hard paths still much worse than v2)

**Impact: HIGH.** The generic regular-path story is much better than before, but the hardest raw
paths still show a large gap near the target.

**What's been done:** Step control now matches v2 more closely (ω extrapolation,
convergence-rate rejection, near-target scaling, β_a, iterative refinement in predictor,
extended precision). The biggest concrete bug found so far was in `StraightLineHomotopy`
Taylor orders 2 and 3: the cross terms coming from varying `t` along the path were missing.
That fix materially reduced katsura step counts.

**What remains:** On the raw tracker trace (`benchmark/compare/trace_tracker.jl`), hard katsura-3
paths can still look like Next `155 / 115 / 270` accepted/rejected/total versus HC raw tracker
`27 / 0 / 27`. That remaining gap is now much more consistent with missing late-path/endgame
behavior than with a generic predictor mismatch.

### 2. No endgame tracker

**Impact: HIGH.** Any system with singular solutions (or solutions approaching infinity) will
fail or return inaccurate results. This limits v3 to well-conditioned square systems with only
nonsingular solutions.

**v2 has:** `EndgameTracker` with Cauchy integral endgame, power series endgame, at-infinity
detection, winding number computation, and singular solution refinement.

**Plan:** Implement `EndgameTracker` wrapping `Tracker`. The tracker infrastructure (adaptive
stepping, Newton corrector, Taylor coefficients) is ready — the endgame is a state machine on
top of it.

### 3. No parallel path tracking

**Impact: HIGH for large systems.** Cyclic-7 has 924 paths; sequential tracking is significantly
slower than v2's threaded `@spawn` approach.

**v2 has:** `Threads.@spawn` with dynamic load balancing in `solve()`.

**Plan:** Infrastructure is ready — `Tracker` is fully self-contained with pre-allocated buffers.
Clone one `Tracker` per thread, partition start solutions, spawn. The main challenge is result
aggregation (lock-free `Vector{PathResult}` push).

### 4. No overdetermined system support

**Impact: MEDIUM.** Users with more equations than variables cannot use v3.

**v2 has:** `RandomizedSystem` (square-up via random linear combinations) +
`excess_solution_check!` (filter false solutions via Newton on original system).

**Plan:** Implement `RandomizedSystem <: AbstractSystem` that wraps a `SystemEvaluator`.
The existing `AbstractSystem` interface and `FunctionWrapper` protocol support this directly.

### 5. No monodromy solver

**Impact: MEDIUM for research users.** Monodromy is v2's most powerful feature for discovering
all solutions to parameterized systems.

**v2 has:** `monodromy_solve` with parameter loops, trace test, `UniquePoints` deduplication,
group actions.

**Plan:** Requires: parameter homotopy (done), `UniquePoints` with `VoronoiTree` (types defined,
not yet used in solve pipeline), loop management + trace test (new code). Large feature surface —
defer until endgame and threading are done.

### 6. No certification

**Impact: LOW for most users, HIGH for rigorous math.**

**v2 has:** `certify(F, result)` using Krawczyk operator with Arblib.jl for interval arithmetic.

**Plan:** Package extension with Arblib.jl. Requires `Interpreter{AcbRefVector}` tape backend
and interval arithmetic operations. Defer to Tier 2.

### 7. No progress bars

**Impact: LOW but visible.** Users expect feedback for long-running solves.

**v2 has:** ProgressMeter.jl integration.

**Plan:** Add `ProgressMeter` as optional dependency, wire into `solve!` loop. Trivial once
threading is done (progress needs to aggregate across threads).

### 8. No multi-homogeneous variable groups

**Impact: LOW.** Polyhedral start system covers most cases where multi-homogeneous would help.

**v2 has:** `variable_groups` keyword, `MultiBezoutIterator`, multi-projective affine charts.

**Plan:** Defer. Polyhedral homotopy already gives BKK-optimal path counts.

## API Differences

| Operation | v2 | v3 |
|-----------|----|----|
| Basic solve | `solve(F)` | `solve(F)` (same) |
| System construction | Implicit in `solve()` | Explicit `System(polys)`, reusable |
| Start system | `:polyhedral` (default) | `Polyhedral()` / `TotalDegree()` types |
| Parameter homotopy | `solve(F, starts; p₁, p₀)` | `solve(F, starts; start_parameters, target_parameters)` (same) |
| Result access | `solutions(r)`, `nreal(r)` | Same API |
| Custom system | Subtype `AbstractSystem` | Same interface, but `FSVec`/`FSMat` passed instead of `Vector`/`Matrix` (transparent via `AbstractVector`) |
| Return codes | Symbols (`:success`) | Scoped enums (`PathResultCode.PATH_SUCCESS`) |
| Compiled mode | `compile=:all` | `compile=CompileMode.COMPILED` (opt-in, RGF-based) |
| Endgame | Automatic | Not available yet |
| Threading | Automatic | Not available yet |
| Certification | `certify(F, result)` | Not available yet |
| Monodromy | `monodromy_solve(F, sols, p)` | Not available yet |

## Priority Order

1. **Endgame / late-path handoff** — correctness blocker and the most likely source of the remaining hard-path tracker gap
2. **Benchmark cleanup + CI** — fix seed handling and step accounting in `benchmark/compare/tracking.jl`, then automate it
3. **Threading** — performance blocker for large systems
4. **Overdetermined** — extends applicability to a common use case
5. **Progress bars** — low effort, high visibility
6. **Direct polynomial compiler** — may reduce complexity for polynomial input
7. **Monodromy** — large feature, research users
8. **Certification** — package extension, niche audience
