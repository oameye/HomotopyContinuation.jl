# v3 vs v2

How HomotopyContinuationNext.jl (v3) differs from HomotopyContinuation.jl (v2), and why.

Last updated: 2026-09-14, against upstream v2.22.4.

## Reproduce

- `make compare` — v3/v2 eval/jac/build ratios and end-to-end comparisons
- `julia --project=benchmark benchmark/compare/ttfx.jl` — fresh-session TTFX comparison
- `make benchmark` — steady-state timings
- `make test` — full core plus certification suite

## Bottom line

v3 is now **feature/capability complete relative to v2.22.4**. The remaining work is API freeze,
release documentation, v3-specific cleanup and performance characterization, not missing v2
functionality.

The parity claim is based on:

1. the July/August testset-by-testset comparison against the v2 suite;
2. the August re-audit against v2.22.1;
3. the September catch-up for the final v2.22.x changes;
4. validation of the integrated merged v3 tree through the permanent CI matrix.

See `09_v2_parity_freeze.md` for the final catch-up record.

## The core design problem in v2

In v2, compiled polynomial systems carry a system-specific identity in their type. That identity
propagates through the homotopy, tracker, endgame and solver stack, so a new polynomial system can
force Julia to specialize and compile a large fraction of the numerical pipeline again.

Conceptually:

```
CompiledSystem{system_id}
  -> homotopy{CompiledSystem{system_id}}
    -> tracker{homotopy{...}}
      -> endgame{...}
        -> solver{...}
```

This is the source of the large first-solve and second-system compilation cost in v2's compiled
modes.

## The v3 type firewall

v3 separates system-specific evaluation code from the solver type domain. `SystemEvaluator` and
`HomotopyEvaluator` are concrete monomorphic firewalls whose callable kernels live behind
`FunctionWrapper`s. A tracker sees the same concrete evaluator type regardless of which polynomial
system produced it.

```
SystemEvaluator
  -> HomotopyEvaluator
    -> Tracker
      -> EndgameTracker
```

A compiled evaluator can therefore be system-specific without making the tracker itself
system-specific.

The consequence is the central v3 invariant:

```
system-specific compiled code
    != system-specific solver type
```

## Important API differences

v3 deliberately does not reproduce every v2 spelling or architecture.

| Operation | v2 | v3 |
|---|---|---|
| Basic solve | `solve(F)` | `solve(F)` |
| System construction | often implicit | explicit reusable `System(...)` |
| Start-system choice | keywords/symbols | typed algorithms (`TotalDegree()`, `Polyhedral()`) |
| Compile mode | `compile=:none/:mixed/:all` | `CompileMode.INTERPRETED/COMPILED/COMPILED_ALL` |
| Many targets | keyword-driven | explicit `Sweep()` route |
| Fix parameters | target-parameter kwargs on several routes | `fix_parameters(F, p)` |
| Parallelism | `threading::Bool` style | positional executor (`Serial`, `Threaded`, `DistributedExecutor`) |
| Monodromy | `monodromy_solve(...)` | `solve(..., Monodromy())` |
| Certification | core package | `HomotopyContinuationNextCertification` subpackage |
| Return codes | symbols | scoped enums |
| Options | keyword bags on verbs | typed algorithm/options structs |

Exact name-level API identity is therefore not the parity criterion. Capability and numerical
behavior are; the final supported public v3 surface still needs an explicit release freeze.

## Where v3 goes beyond v2

### 1. Compilation predictability

The monomorphic evaluator firewall prevents a new input system from creating a new tracker and
endgame type chain. This is the main architectural reason for v3.

### 2. Pure-Julia symbolic/evaluation pipeline

v3 does not depend on the old SymEngine-based ModelKit architecture. Polynomial and expression
front ends lower into a shared instruction representation, with pure-Julia CSE and optional
RuntimeGeneratedFunctions code generation.

### 3. Separate lightweight core and certification package

Arblib is isolated in `HomotopyContinuationNextCertification`; users who only solve systems do not
pay its load/invalidation cost.

### 4. Distributed execution

`DistributedExecutor` provides multi-process execution across the major path-tracking routes and
monodromy. v2 has no equivalent general executor abstraction.

### 5. Lossless NID incompleteness

When decomposition exhausts its iteration budget, v3 retains unresolved witness orbits with
`Irreducibility.UNKNOWN`. The result distinguishes

```
proved irreducible components
+
unresolved witness sets
```

instead of silently dropping unresolved geometry.

### 6. Stronger expression/certification stack

The v3 expression IR, DoubleF64 kernels, rectangular interval arithmetic and Acb backend share one
operation vocabulary. Principal-branch behavior and branch-cut rejection are explicit for
operations such as `log` and real powers.

## September 2026 late-v2 catch-up

The final upstream-delta audit covered the changes merged after the earlier parity snapshot.
Relevant v2 changes now represented in v3 include:

- non-finite predictor trust-region fallback;
- NID randomization and tolerance propagation;
- full/zero-dimensional `LinearSubspace` support;
- corrected witness/intersection coordinate contracts;
- the Taylor positive-integer-power zero-constant-term case;
- principal-branch `log`;
- monodromy endpoint-admission hardening;
- fixed-parameter custom homotopies.

Two upstream changes are architecture-specific rather than missing capabilities:

- v2's locks around global compiled-system caches have no v3 analogue because v3 has no global
  per-system compile table;
- v2's polyhedral `show_progress` plumbing follows a MixedSubdivisions call path that v3 replaced
  with its own canonical mixed-cell construction.

## NID policy difference

Upstream v2 increased its default decomposition iteration allowance substantially. v3 currently
keeps a smaller default budget (`max_iters = 50`) but has different semantics on exhaustion:
unresolved points remain in the result as `UNKNOWN` witness sets and are queryable through
`unresolved_witness_sets` and `unresolved_degree`.

This is a deliberate policy difference, not a missing feature. Increasing the default remains a
performance/usability decision for the release freeze.

## Performance snapshot

Historical measurements from the v3 development branch showed:

- total-degree solving about 1.8–3.6x faster than v2 on the comparison set;
- polyhedral solving roughly at parity (about 0.95–1.01x);
- cold load + construction + first solve around 10.6 s versus about 45 s for v2's default compiled
  route.

Those values are development snapshots rather than promises. Current numbers should always be
reproduced from the benchmark scripts.

A direct final `COMPILED_ALL` versus v2 `:all` comparison is still worth recording before release;
that is performance characterization, not feature completion.

## What is intentionally not ported

The following are v2 implementation architecture rather than user capabilities and are not parity
targets:

- `CompiledSystem` / `InterpretedSystem` / `MixedSystem` as public architecture;
- the global `set_default_compile` state;
- the global compiled-system caches and their locking tests;
- SymEngine-specific ModelKit internals;
- TreeViews/Juno display machinery;
- implementation-specific cache and wrapper types whose purpose disappears behind the v3
  evaluator firewall.

## Remaining work

There are no known remaining v2 feature gaps. Work before a release should be categorized as:

1. public API stabilization and extension-surface declaration;
2. release/user documentation and migration guidance;
3. v3-specific distributed-executor reach into the remaining internal witness operations;
4. benchmark/TTFX characterization and regression monitoring;
5. internal cleanup/refactoring that does not alter solver semantics.

mapping see `09_v2_parity_freeze.md`.
